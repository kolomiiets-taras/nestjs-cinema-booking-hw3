# Cinema Booking API

REST API сервісу бронювання місць у кінотеатрі на NestJS: фільми, зали, сеанси й бронювання.
Дані зберігаються в MongoDB (Mongoose). Маршрути й формат відповідей ті самі, що й у версії на PostgreSQL;
змінилися модель даних і спосіб гарантувати, що одне місце не буде заброньоване двічі.

## Вимоги

- Node.js 22 LTS (22.13+) або новіший, npm
- Docker з Docker Compose (MongoDB 7 запускається в контейнері)

## Запуск

```bash
# 1. встановлення залежностей
npm install

# 2. змінні оточення (за потреби змініть значення)
cp .env.example .env

# 3. підняти MongoDB у Docker Compose (у фоні)
docker compose up -d

# 4. (необов'язково) заповнити базу даними для перевірки
npm run seed

# 5. запуск у dev-режимі (з перезапуском при змінах)
npm run start:dev
```

Сервер: http://localhost:3000, документація Swagger: http://localhost:3000/docs

Зупинити базу: `docker compose down` (дані лишаються в іменованому volume `cinema-mongodata`);
`docker compose down -v` — зупинити й видалити дані.

Образ — `mongo:7` (standalone, без replica set: транзакції застосунку не потрібні). Образи `mongo:8.x` на
ядрах Linux 6.19 і новіших не стартують (відома несумісність, MongoDB SERVER-121912), тому зафіксовано
мажорну версію 7.

### Змінні оточення (`.env`)

Приклад файлу `.env` (те саме лежить у `.env.example`):

```dotenv
PORT=3000
NODE_ENV=development

MONGO_PORT=27017
MONGO_ROOT_USERNAME=cinema
MONGO_ROOT_PASSWORD=cinema

MONGODB_URI=mongodb://cinema:cinema@localhost:27017/cinema?authSource=admin
```

| Змінна | Хто читає | Опис | Приклад |
|---|---|---|---|
| `PORT` | застосунок | Порт HTTP-сервера | `3000` |
| `NODE_ENV` | застосунок | `development`, `production` або `test` | `development` |
| `MONGODB_URI` | застосунок, seed, e2e-тести | Рядок підключення до MongoDB | `mongodb://cinema:cinema@localhost:27017/cinema?authSource=admin` |
| `MONGO_PORT` | `docker-compose.yml` | Порт MongoDB на хості; контейнер публікує свій `27017` саме на нього | `27017` |
| `MONGO_ROOT_USERNAME` | `docker-compose.yml` | Користувач, якого образ створює при першому старті з порожнім volume | `cinema` |
| `MONGO_ROOT_PASSWORD` | `docker-compose.yml` | Його пароль | `cinema` |

Змінні застосунку проходять валідацію (`src/config/environment-variables.ts`, декоратори `class-validator`,
`ConfigModule.forRoot({ validate })`): без `MONGODB_URI` або з рядком, що не починається з `mongodb://` /
`mongodb+srv://`, застосунок не стартує й пише, яка змінна не пройшла перевірку. Підключення —
`MongooseModule.forRootAsync`, рядок береться з `ConfigService`.
Якщо порт `27017` на машині вже зайнятий, змініть `MONGO_PORT` (наприклад, на `27018`), той самий порт
у `MONGODB_URI`, і перезапустіть `docker compose up -d`.

### Засівання (`npm run seed`)

`src/seed.ts` піднімає контекст застосунку (та сама валідація конфігурації й ті самі моделі) і додає 3 фільми,
2 зали, 4 сеанси в різні дати (15–18 січня 2027) з розгорнутими масивами місць і 1 бронювання на 2 місця.
Працює на порожній базі. Фільми, зали й сеанси записуються через upsert за природним ключем (назва фільму,
назва залу, фільм + зал + час), а бронювання — тим самим умовним оновленням, що й API («усі місця вільні»):
повторний запуск нічого не дублює й пише `Seed: data already present, nothing to create.`

## Модель даних

Три колекції: `films`, `halls`, `showings`. Схеми описані класами з `@Schema` / `@Prop`
(`src/*/schemas/*.schema.ts`) і підключені у feature-модулях через `MongooseModule.forFeature`.

| Колекція | Поля | Обмеження |
|---|---|---|
| `films` | `title`, `durationMinutes`, `releaseYear` | усі `required` |
| `halls` | `name`, `rows`, `seatsPerRow` | усі `required`; **унікальний індекс на `name`** (без урахування регістру — collation strength 2) |
| `showings` | `film` (ObjectId → `films`), `hall` (ObjectId → `halls`), `startsAt`, `price` (копійки), `seats[]`, `bookings[]` | `film`, `hall`, `startsAt`, `price` — `required`; індекси `film`, `hall`, `{ startsAt, _id }`, `bookings._id` |

Вкладені документи сеансу описані окремими класами зі своїми схемами (`SchemaFactory.createForClass`):

- `Seat` — `{ row, seat, bookingId }`, `bookingId: null` для вільного місця. Масив заповнюється при створенні
  сеансу: зал на 3 ряди по 5 місць дає 15 елементів. Це джерело істини про зайнятість.
- `Booking` — `{ _id, seats: [{ row, seat }], totalPrice, createdAt }`. `_id` генерується в коді до запису,
  бо той самий id потрапляє і в `seats[].bookingId`. Перелік місць дублює `seats`, щоб віддати бронювання
  без перебору всього залу.

Місця залу в документі залу не зберігаються — перелік обчислюється з `rows × seatsPerRow`.

### Чому місця й бронювання лежать усередині сеансу

Бронювання — це дві зміни одночасно: позначити місця зайнятими і зберегти запис бронювання. У PostgreSQL їх
об'єднувала транзакція. У MongoDB неподільне лише оновлення **одного** документа; зміна кількох документів
(наприклад, окремої колекції `bookings` і документа сеансу) потребує транзакції, а транзакції працюють тільки
на replica set. Якщо ж і місця, і бронювання лежать у документі сеансу, обидві дії робить один `updateOne`:
або застосовуються обидві, або жодна, і ніякої транзакції не потрібно — підходить звичайний standalone-сервер.

Умову «усі місця вільні» перевіряє той самий запит, що їх займає, тому два одночасні запити на одне місце
виконаються по черзі, і другий просто не знайде документа (409). Читати документ, перевіряти масив у коді
і потім писати не можна: між читанням і записом місце може зайняти інший запит.

Вкладення тут допустиме, бо розмір масивів обмежений: місць у залі кілька сотень, бронювань на сеанс не більше,
ніж місць, тож документ сеансу не росте безмежно (ліміт документа MongoDB — 16 МБ). Якби дані накопичувалися
без обмеження (наприклад, історія бронювань за роки), вкладення не підійшло б — їх винесли б в окрему колекцію.

## Бронювання

`POST /showings/:id/bookings` (`src/showings/bookings.service.ts`):

1. DTO перевіряє форму: непорожній масив, у кожного елемента цілі додатні `row` і `seat`, **без повторів**
   (два однакові `$elemMatch` задовольнило б одне вільне місце, і в `bookings` потрапила б подвійна ціна).
2. Сервіс читає сеанс лише з ціною та залом (без масивів): немає сеансу — 404; місце поза `rows × seatsPerRow` —
   400 (фільтр оновлення не відрізняє неіснуюче місце від зайнятого, тож без цієї перевірки вийшов би 409).
3. Один `updateOne`:
   - фільтр — `_id` сеансу + `$and` з `$elemMatch: { row, seat, bookingId: null }` для кожного місця;
   - `$set: { 'seats.$[target].bookingId': bookingId }` з `arrayFilters: [{ $or: [{ 'target.row', 'target.seat' }, …] }]`;
   - `$push: { bookings: { _id: bookingId, seats, totalPrice, createdAt } }`.
4. `matchedCount === 0` → 409, і жодне місце не бронюється (`modifiedCount` не годиться: він 0 і тоді, коли
   документ знайдено, але нічого не змінилося).

`DELETE /bookings/:id` — теж один `updateOne`: фільтр `{ 'bookings._id': id }` знаходить сеанс за вкладеним
бронюванням, `$set` повертає `bookingId: null` місцям (`arrayFilters: [{ 'target.bookingId': id }]`), `$pull`
видаляє бронювання з масиву. `matchedCount === 0` → 404.

`GET /bookings` збирає бронювання з усіх сеансів агрегацією (`$unwind` масиву `bookings`), відсортовані за часом
створення.

## Перевірка

- `requests.http` — усі маршрути в порядку фільм → зал → сеанс → бронювання і запит на кожну описану помилку.
  Відкрити у VS Code з розширенням
  [REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client) і виконувати запити
  згори вниз на запущеному сервері; id підставляються автоматично зі змінних. Назви залів містять
  `{{$timestamp}}`, тому файл можна проганяти повторно на тій самій базі. Якщо сервер запущено на іншому порту,
  змініть `@baseUrl` на початку файлу.
- `npm run test:e2e` — автоматичні e2e-тести (потрібен запущений контейнер). Тести не чіпають робочу базу:
  вони працюють з окремою базою `<назва бази з MONGODB_URI>_test` на тому самому сервері, видаляють її перед
  запуском і після. Перевіряються всі маршрути й помилки, подвійне бронювання (409, документ не змінюється)
  і паралельні запити на те саме місце (рівно один 201, решта 409). Скрипт запускає Jest з
  `--experimental-vm-modules`: драйвер MongoDB 7 підвантажує модуль `os` через динамічний `import()`,
  який без цього прапорця в пісочниці Jest недоступний.

### Ідентифікатори

Усі `id` — ObjectId: рядок із 24 шістнадцяткових символів. Параметри маршруту перевіряє `ParseObjectIdPipe`,
`filmId` / `hallId` у тілі й `filmId` у query — `@IsMongoId` у DTO; некоректний формат дає 400 з поясненням
ще до звернення до бази. Коректний за формою id неіснуючого документа дає 404 (для `filmId` / `hallId`
у `POST /showings` — 400, бо це помилка в тілі запиту).

```json
{
  "statusCode": 400,
  "message": "Invalid id \"abc\": expected a MongoDB ObjectId: 24 hexadecimal characters (0-9, a-f), e.g. 6730f1c2b0e7a52d7e9b8a0c",
  "path": "/films/abc",
  "timestamp": "2026-11-25T18:00:00.000Z"
}
```

У відповідях `id` — рядок: документи перетворюються класами DTO (`FilmResponseDto`, `HallResponseDto`,
`ShowingResponseDto`, `BookingResponseDto`), `_id` і `__v` у тіло не потрапляють.

### `GET /showings`

Усі параметри необов'язкові й комбінуються:

| Параметр | Значення | За замовчуванням |
|---|---|---|
| `filmId` | ObjectId фільму | — |
| `date` | `YYYY-MM-DD` — сеанси, що починаються цієї доби (UTC) | — |
| `page` | ціле число від 1 | `1` |
| `limit` | ціле число від 1 до 100 | `20` |
| `sort` | `asc` або `desc` — порядок за часом початку | `asc` |

Фільтр, сортування (`startsAt`, при рівності — `_id`), `skip` / `limit` і `countDocuments` для `total`
виконуються запитами до бази; масиви `seats` і `bookings` відкидаються проєкцією, назви фільму й залу
розкриваються через `populate`.

```json
{
  "items": [
    {
      "id": "6730f1c2b0e7a52d7e9b8a0c",
      "film": { "id": "6730f1c2b0e7a52d7e9b8a01", "title": "Dune: Part Two" },
      "hall": { "id": "6730f1c2b0e7a52d7e9b8a02", "name": "Red Hall" },
      "startsAt": "2030-05-10T18:00:00.000Z",
      "price": 12500
    }
  ],
  "total": 3,
  "page": 1,
  "limit": 20
}
```

### Формат помилки

Глобальний фільтр винятків (`src/common/filters/http-exception.filter.ts`) повертає кожну помилку в одному
форматі `{ statusCode, message, path, timestamp }`. Для помилок валідації `message` — масив повідомлень.
Непередбачені помилки (наприклад, збій бази) повертаються як 500 `Internal server error` без тексту помилки
бази; деталі пишуться лише в лог сервера.

## Рішення

- **Видалення фільму або залу** з сеансами — 409 з поясненням. Зовнішніх ключів у MongoDB немає, тому сервіс
  перевіряє залежні сеанси запитом (`exists` по індексованому полю `film` / `hall`).
- **Унікальна назва залу** гарантується індексом у схемі; помилку дубліката ключа MongoDB (код `11000`) сервіс
  перетворює на 409, тож і два одночасні запити з однаковою назвою не створять дубліката.
- **Ціни** зберігаються в копійках (цілі числа): `12500` = 125 грн. `totalPrice` = ціна сеансу × кількість місць.
- **Фільтр `date`** — доба за UTC: `startsAt >= date 00:00Z` і `< наступна доба 00:00Z`.
- **Списки** `GET /films` і `GET /halls` впорядковані за назвою, `GET /bookings` — за часом створення.
- **Розподіл перевірок**: DTO з `class-validator` перевіряють форму запиту (наявність, тип, діапазон, формат
  ObjectId, унікальність місць у масиві); сервіси — доменні правила, для яких потрібен стан бази (існування
  фільму/залу, межі залу, зайнятість місць, залежні сеанси). `ValidationPipe` глобальний з `whitelist: true`.
- **Swagger** (`/docs`) описує формат ObjectId для кожного параметра `:id` (опис, `pattern`, приклад), коди
  відповідей кожного маршруту, сторінку розкладу (`ShowingsPageDto`) і формат помилки (`ErrorResponseDto`).

## Структура

```
src/
  config/        валідація змінних оточення
  common/        фільтр винятків, формат помилки, ParseObjectIdPipe, Swagger-декоратор для ObjectId
  films/         FilmsModule    — фільми (schemas/film.schema.ts)
  halls/         HallsModule    — зали та обчислення місць (schemas/hall.schema.ts)
  showings/      ShowingsModule — сеанси, розклад, карта місць і бронювання
                 (schemas/showing.schema.ts, seat.schema.ts, booking.schema.ts)
  seed.ts        засівання бази
  setup-app.ts   глобальні ValidationPipe, фільтр винятків і Swagger
docker-compose.yml  MongoDB 7
```

Модулі звертаються один до одного лише через експортовані сервіси. Бронювання розміщено в модулі сеансів,
бо вони зберігаються всередині документа сеансу. `films` і `halls` пов'язані з `showings` у дві сторони
(сеанс перевіряє існування фільму й залу, а видалення фільму чи залу перевіряє наявність сеансів) —
цю зустрічну залежність розв'язано через `forwardRef`.
